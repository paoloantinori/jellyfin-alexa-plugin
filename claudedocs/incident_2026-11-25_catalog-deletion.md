# Incident runbook: Amazon-side deletion of the six interactionModel catalogs (2026-11-25)

Date of incident: 2026-11-25. Status: closed (all six catalogs recreated and ER-live; deleter never identified). This document is the runbook of record for the incident class: it records what happened, how the diagnosis went right and wrong, the manual recovery as executed, and the one-click recovery that replaces it. The standing triage rule it produced is also encoded in CatalogLivenessChecker (JF-966) and in the memory node whole-family-cross-locale-death-check-catalogs-first.

## (a) Timeline and evidence

Between roughly 15:00 and 15:45 local on 2026-11-25, all six SMAPI interactionModel catalogs the plugin had created (artist, album, series, audiobook, movie, song) stopped existing on Amazon's side: a get-catalog against each stored id returned a clean 404. That window is when the family's entity resolution went NONE, not an observed atomic delete (no API names the deletion moment; see section f). The first surface was behavioral, not administrative: whole slot-type families read ER_SUCCESS_NONE cross-locale in profile-nlu (exact-name artist forms such as "suona radiohead" and "play coldplay" selected no intent in every locale, evergreens included), while the plugin's own LocaleModelStatuses ledger still read SUCCEEDED for every locale. That divergence (voice selection dead, model build status healthy) is the fingerprint of the catalog layer dying under a healthy model: the live models kept referencing catalog versions whose parent catalogs no longer resolved.

TIMESTAMP CAVEAT (read this before quoting any absolute time below): the two timestamp families recorded for the recovery do not reconcile. The SMAPI version stamps say the fresh catalogs' versions were minted 15:09 through 15:33, while the session's wall-clock recollection placed the manual recovery between 16:00 and 16:35; a one-hour skew between the two is exactly what SMAPI stamps recorded in UTC against local CET times would produce, but that explanation was never verified, and the same day's first closure note already demonstrated the independent failure mode of a mis-anchored wall clock (it claimed the ER landing at 18:10 to 18:20 before artifact stamps corrected it to 17:16 to 17:18). Treat the version stamps and the value counts as the hard evidence and every absolute wall clock as soft; the relative gaps below were computed by the incident session treating stamps and terminal times as one frame. Version counts on the fresh ids: artist v8 at 1137 values (eight versions minted in rapid succession, one per locale leg, because per-locale phonetic synonyms differ), album v8 at 850, audiobook v9 at 234, series v8 at 160, movie v8 at 103. Entity resolution came back non-atomically: series (160 values) was ER-live at roughly 40 minutes after its version creation, while artist (1137 values plus the synonym family) landed about 1h45 after its version creation, with individual values (coldplay before pink floyd and radiohead) resolving minutes apart while the index was still filling. The lesson generalizes: wall-clock claims about incidents come from artifact stamps, never from reconstructed memory.

## (b) The unknown deleter and the ruled-out candidates

No deletion agent was ever identified. SMAPI offers no deletion audit trail (see section f), so the elimination is one-sided: everything of ours that could delete a catalog was examined and none matched. The ablation worker's deletes were synthetic-only and every one was refused by SMAPI (synthetic catalog ids do not exist Amazon-side). The JF-949 song-catalog teardown ran with its flag ON but is scoped to the song catalog alone and deletes through the plugin's own logged path, which showed no delete calls in the window. The 13:28 catalog sync succeeded healthy and left every stored id answering. Nothing of ours ran in the deletion window except a clean DLL redeploy and an es-US model rebuild, neither of which touches catalog resources. The practical conclusion: assume an Amazon-side cause (their console, an account-level action, or a backend purge) until evidence says otherwise, and spend effort on detection and recovery rather than on guarding a phantom self-inflicted path.

## (c) The diagnosis chain and the standing triage rule

The incident's first hour went to the wrong layer: the whole-family ER NONE readings were probed as an NLU hypothesis (JF-964 conjunction experiments) while every catalog was already 404 and the plugin's surfaces reported healthy. The lesson is now a standing rule, enforced in two places (the CatalogLivenessChecker error text and the JF-971 test-side triage verdict): a whole slot-type family dying cross-locale is an INFRASTRUCTURE signature, not an NLU regression. Check catalog liveness FIRST, before any graph, lab-battery, or conjunction theory. The check is one get-catalog per stored id on the route family the catalogs were created on (the ManagementApi ReferenceCatalogManagement Get call, the same one the plugin's sync uses); only a clean 404 marks a catalog dead, because a network error, a 401 from an expired token, a 5xx, or a timeout is UNKNOWN and must never trigger the destructive heal. Since JF-966 the plugin runs this probe automatically from the sync task's skip path, so a future deletion surfaces as a loud error log plus a durable CatalogIdsDead caveat on the locale-status ledger within one restart, without anyone thinking about NLU at all.

## (d) The manual recovery as executed (fallback only)

This is the path that was actually used on 2026-11-25, kept here as the fallback for when the plugin itself is down or unloaded. It is fragile container surgery; do not prefer it when section (e) is available.

1. Back the plugin config up first: fetch it via the API and save it (the incident used /tmp/alexa_config_pre_recovery.json). The XML on disk, not the JSON API, is the source of truth for the catalog id fields.
2. Null the six catalog id elements in the on-disk plugin XML. The edit was done OUT of the container because the container has no python3, and sed alternation is unusable for this file: the catalog id values sit next to composite tokens that contain pipe characters, on which sed alternation breaks. Copy the file out (podman cp), edit it with a real editor, copy it back.
3. After the podman cp back, run the chown to abc:abc on the file (podman cp writes as root, and a root-owned config can keep the whole server from booting).
4. Backdate or clear the user's LastCatalogSync so the sync gate does not skip the user for the rest of its 12h window, then restart Jellyfin.
5. The next catalog sync pass recreates all six catalogs with fresh ids and re-uploads values (expect roughly 30 minutes for a multi-locale run), then the model PUTs re-wire every locale to the fresh catalog versions.
6. Wait out ER propagation before escalating: hours-scale propagation is normal for large catalogs and it is per value, not atomic (see section a's numbers). Probe one exact-name utterance per family with profile-nlu rather than re-reading statuses, because no API exposes ER-index readiness.

## (e) The one-click recovery (the path of record)

Since JF-967 the plugin exposes the guarded admin action POST /alexaskill/api/catalog/recreate (RequiresElevation), wired to the "Recreate Catalogs" button in the plugin configuration page's catalog section. The action: resolve the plugin user from the body's userId; null ALL SIX stored catalog ids unconditionally (a whitespace-garbage id is nulled too); clear LastCatalogSync (the force-next-sync null); write a recovery audit row (Source "CatalogRecovery") into every locale-ledger row naming the OLD ids that were nulled and the timestamp clear; strip the CatalogIdsDead caveat from any row carrying it (the recreate invalidates the dead finding); persist the user mutations and the ledger sweep through ONE locked save; then queue the CatalogSyncTask through Jellyfin's ITaskManager, the same queue the dashboard's Run button uses, so the recreate runs on the next pass instead of waiting out the interval. The action never calls SMAPI itself, so it works even while Amazon-side state is broken, and it is idempotent: a user with nothing to clear gets an honest nothingCleared response and no writes. To call it directly instead of the button: POST {"userId": "<the plugin user's guid>"} to alexaskill/api/catalog/recreate with an admin token. What to expect: the response reports the nulled ids and the queue outcome; the queued sync recreates the catalogs (watch the locale-status panel in the plugin configuration page as its rows go through the fresh PUT cycle); then wait out the ER propagation per section (d) step 6.

## (f) The forensic gap

SMAPI offers no deletion audit trail that we could find: no event log, no change history, nothing that names an actor for a deleted catalog. The vendor-scoped catalog list (/v0/catalogs) does not list interactionModel catalogs at all; it shows only AlexaMusic-typed entries, so it cannot even confirm existence, let alone deletion. Reading a catalog's values back (the strongest "the data is there" probe) uses ask smapi get-interaction-model-catalog-values -c <id> --vers <version>; note the flag is --vers, and --max-results makes the CLI emit garbage (the literal string "2.30.7"), so page with --next-token using the real token from the previous response. The catalog update-status endpoint (get-interaction-model-catalog-update-status with --update-request-id "~current") 500'd on our fresh catalogs during the incident, so treat it as unreliable. These gaps are why detection in this incident class is a plugin-side liveness probe (JF-966) rather than an Amazon-side notification.
