## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Surfaced by the JF-424 review (confirmed finding). The precompute cache (Jellyfin.Plugin.AlexaSkill/Alexa/Playback/NextTrackPrecomputeCache.cs) is keyed by deviceId and validated by the current track's token, but the play token is the BARE ITEM GUID (see BaseHandler's stream/play token construction), so a token match identifies an ITEM, not a playback session. A stale entry can therefore be served for a later, unrelated playback of the same item.

Failure scenario (all confirmed against source by the JF-424 review): queue [A,B]; PlaybackStarted(A) stores entry(A->B); the user skips A so no matching NearlyFinished consumes it; the user clears the queue (ClearQueueIntentHandler clears the DeviceQueueManager queue but NEVER calls NextTrackPrecomputeCache.Invalidate, which currently has ZERO production callers); the user replays A as a single-item play; PlaybackStarted(A) early-returns last-in-queue (PlaybackStartedEventHandler.TryPrecomputeNext) and stores nothing; within the 15-min TTL a NearlyFinished(A) token-MATCHES the stale entry and PlaybackNearlyFinishedEventHandler enqueues B after a single-item play (bypassing PostPlay/radio resolution). Additionally, in the cache-hit branch, DeviceQueueManager.MoveTo(B) returns false (B absent from the queue) yet the handler still sets queue.CurrentItemId = B, dangling the queue pointer.

Precondition: PreEnqueueOnStart opt-in (default false), so exposure is limited to opted-in users.

Suggested directions (pick the minimal correct one): validate the cached nextItemId against the live device queue before serving; and/or wire NextTrackPrecomputeCache.Invalidate into queue-changing paths (clear queue at minimum); and/or only set CurrentItemId when MoveTo succeeded.
<!-- SECTION:DESCRIPTION:END -->
