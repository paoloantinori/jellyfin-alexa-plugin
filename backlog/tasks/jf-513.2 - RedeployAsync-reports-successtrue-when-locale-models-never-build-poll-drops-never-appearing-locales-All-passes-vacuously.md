## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found by the JF-513 code review (verified by reading the code): the rebuild endpoint's verification chain can report success=true even when locale models were accepted but never built, which is exactly the failure class JF-513 was filed on ('saved models that never build'), so the outcome of the JF-513 redeploy itself is not guaranteed verifiable through this path.

Mechanism (Jellyfin.Plugin.AlexaSkill/Alexa/ModelDeployment/InteractionModelRedeployer.cs):
- PollLocaleBuildStatusAsync (lines ~161-206) only records a locale in `results` when it appears in status.InteractionModel with a non-IN_PROGRESS state; a locale whose build never appears in the status map, or that stays IN_PROGRESS past the MaxStatusPolls x PollInterval budget, is silently absent.
- RedeployAsync (~line 78): `deployedResults` = localeResults filtered to deployedLocales; `success = deployedResults.All(r => r.Value.Success) && updateFailures.Count == 0` is vacuously true for every dropped locale. The log line does show the arithmetic mismatch ('Redeployed 17 interaction models: 12 succeeded, 0 failed') but the returned boolean and the endpoint response say success.
- The single-locale path already handles this correctly (ModelDeploymentManager.WaitForLocaleModelBuildAsync maps TIMEOUT to failed), proving the gap is local, not platform.

Fix direction: after polling, every locale in deployedLocales must have a deployedResults entry; treat missing ones as failed (state TIMEOUT / NEVER_BUILT) so All() cannot pass vacuously.

Relevance to JF-513: the task's acceptance step ('verify with get-skill-status that 17 locales report SUCCEEDED') must not rely solely on this endpoint's success flag; check the per-locale map too.
