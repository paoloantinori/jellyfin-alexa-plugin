## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Code-review finding (2026-08-31, high effort) on the JF-419 implementation. BaseHandler.cs:1492 (IsArtistIndexWarming gate) + ArtistIndexService.cs:122.

DEFECT: ArtistIndexService.RefreshAsync runs once from StartAsync; its catch (Exception) only logs, leaving _isReady=false. The only re-trigger is a MusicArtist add/remove event. If the startup load throws ONCE (e.g. DB still migrating after the restart that JF-419 itself targets), IsArtistIndexWarming returns true FOREVER, so PlayArtistSongs/PlaySong/PlayAlbum/FindSong answer every request with the session-ending SkillWarmingUp message until another server restart. The pre-JF-419 code fell back to the database search, which was the safety net this gate removed.

FIX SHAPE (choose one, smallest that works): periodic background retry of RefreshAsync while !_isReady; or lazy retry (attempt refresh on first request that finds the gate closed, once per N minutes); or rethrow from StartAsync so the host restarts the hosted service. Preserve JF-419's intent: during a genuinely cold load, still return the warming Tell response.

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
## Implementation Plan (JF-419.1)

**Approach**: periodic self-disarming retry inside ArtistIndexService (option (a) from the task's fix shapes). Lazy retry (b) couples the service to request flow and risks a retry storm per request while the DB is down; rethrow from StartAsync (c) makes plugin startup host-dependent. A one-shot re-arming Timer is self-contained, reuses the existing lock-protected RefreshAsync, and recovers within the minute the SkillWarmingUp message promises ("riprova tra un minuto").

**Changes (ArtistIndexService.cs only):**
1. `private Timer? _retryTimer;` guarded by the existing `_debounceLock` (lock order: only _refreshLock -> _debounceLock nesting inside RefreshAsync; no reverse nesting, no deadlock).
2. `internal TimeSpan FailedLoadRetryInterval { get; set; } = TimeSpan.FromSeconds(30);` (InternalsVisibleTo exists; a ctor param would break MS.DI resolution which does not support optional params).
3. `StartAsync`: after RefreshAsync, `ScheduleRetryIfNotReady()` (no-op when ready).
4. `ScheduleRetryIfNotReady()`: one-shot timer (due = FailedLoadRetryInterval, period = infinite) whose callback runs RefreshAsync(CancellationToken.None) in try/catch, then in finally disarms itself and re-arms only if still !_isReady (a library-change refresh succeeding in between also disarms via the success path).
5. RefreshAsync success path: disarm _retryTimer (covers recovery via the debounce path).
6. Dispose: dispose _retryTimer under the lock.

**Tests (ArtistIndexServiceTests.cs, TDD, red first):**
1. StartAsync_FailedInitialLoad_RetriesAndRecovers: GetItemList throws once then returns artists; interval 50ms; poll IsReady with timeout; assert recovery + Count.
2. StartAsync_PersistentFailure_KeepsRetrying: GetItemList always throws; after ~200ms GetItemList callCount > 1 and still !IsReady.
3. StartAsync_SuccessfulLoad_DoesNotScheduleRetry: interval 50ms, wait 150ms, GetItemList callCount == 1.
Handler-side warming behavior is already covered by SkillWarmingUpTests.cs (parent JF-419); IsArtistIndexWarming flips with IsReady, so service-level IsReady assertions cover AC #1/#2's gate-lifting.

**Verification**: dotnet build (0 warnings) + full dotnet test (no --no-build), then /simplify + /code-review gates, commit with gate markers, task finalization.

## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->
JF-419.1: the artist index now self-recovers from a failed startup load; the warming gate can no longer wedge permanently.

WHAT CHANGED (commit 36f11af, ArtistIndexService.cs + tests)
- RefreshAsync's finally arms ScheduleRetryIfNotReady(): a one-shot Timer (FailedLoadRetryInterval, default 30s) that re-runs the load and re-arms on failure, until ANY load succeeds (initial, retry, or library-change refresh; the success path disarms it). One failed load (DB still migrating) now heals within ~30s instead of refusing all 4 gated handlers until a restart.
- Happy path cost is zero: no timer exists after a successful load (test-locked), request path untouched.
- Dispose hardening (same race class, found during review): _disposed is volatile and set before the lock; in-lock re-checks added to BOTH ScheduleRefresh and ScheduleRetryIfNotReady so neither an event nor a retry callback can arm a timer after cleanup.
- Internal FailedLoadRetryInterval test hook (InternalsVisibleTo; not a ctor param: MS.DI cannot resolve optional parameters). Fixed 30s deliberately mirrors the SkillWarmingUp 'riprova tra un minuto' promise; no backoff (rationale in notes).
- Tests (TDD, red first): recovery after one failed load; persistent failure keeps retrying without a storm (max one in-flight attempt, _refreshLock serializes); no retry after a successful load. Helper CreateServiceWithLoad collapses the mock setup.

WHY: JF-419's warming gate removed the DB-search safety net; without recovery, one transient startup failure made the skill answer every artist request with the warming message until another restart (live-incident class).
