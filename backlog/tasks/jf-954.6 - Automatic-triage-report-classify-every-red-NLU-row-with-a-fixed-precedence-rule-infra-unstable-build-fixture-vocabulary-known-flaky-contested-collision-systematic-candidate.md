## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
## Why

This is the payoff task of JF-954. After a live NLU suite, a human currently reads every red row and guesses its cause. On 2026-11-23 that took most of a day for 45 rows and required extra lab rounds at about 20 minutes each. The earlier subtasks produce four independent deterministic signals per row. This task combines them into ONE verdict per red row using a fixed precedence, groups the rows into families, and prints a report a maintainer can act on in minutes. Read parent JF-954 first; its "Rules that apply to EVERY subtask" section is binding.

Inputs provided by the dependencies (all in `scripts/nlu_static/`):
- JF-954.5: the ledger (`tests/integration/results/nlu-*.jsonl`) with row outcomes, `failure_kind`, per-locale `model_sha256`, live identity at start and end, and the statistics functions (`flips_same_model`, `rebuilt_during_run`).
- JF-954.3: `check_fixture_rows(effective_model, rows)` giving `PRESENT`, `ABSENT`, `NO_ENTRY_IN_UTTERANCE`, `FIXTURE_SLOT_UNKNOWN`, `NOT_APPLICABLE` per pinned slot, with `type_kind`.
- JF-954.4: `classify_fixture_row(row, effective_model)` giving `UNCONTESTED`, `CONTESTED` (with `rivals`), `NO_SAMPLE_MATCH`.
- JF-954.2: the token collision findings (`CARRIER_VS_VALUE` with the intent that carries the word and the intents that use the type).

## Verdicts and precedence (first matching rule wins; implement in exactly this order)

For each row of the chosen session whose outcome is `fail` or `error`:

1. `INFRA`: outcome is `error` (`failure_kind` is `smapi_error`). The probe failed; nothing can be said about routing.
2. `UNSTABLE_BUILD`: `rebuilt_during_run` is true for the row's locale. The model changed while the suite ran; the row must be re-probed, not analysed.
3. `FIXTURE_VOCAB`: the fixture-vocabulary check reports `ABSENT` or `FIXTURE_SLOT_UNKNOWN` for the row in the effective model. When a catalog snapshot is supplied the effective model is the snapshot one, and the verdict detail says `absent in live catalog`; without a snapshot it says `absent in committed seed`.
4. `KNOWN_FLAKY`: in the sessions BEFORE the chosen one, the row has `flips_same_model` of at least `--flaky-min-flips` (default 1) within the last `--history` sessions (default 10).
5. `CONTESTED`: the matcher classification is `CONTESTED` or `NO_SAMPLE_MATCH` AND the row's `actual_intent` is one of the `rivals`. Detail lists the rival sample and whether it is at least as specific as the expected one.
6. `TOKEN_COLLISION`: a `CARRIER_VS_VALUE` finding exists in the locale where the carrying intent is one of the expected intents and the row's `actual_intent` uses the colliding type, and the colliding entry occurs in the utterance.
7. `SYSTEMATIC_CANDIDATE`: none of the above. The row is uncontested or lost to an intent with no static reading, has no flaky history and its vocabulary is present. These rows are the ones a human must look at first.

Every row also carries the raw signals regardless of verdict (`vocab_status`, `match_classification`, `rivals`, `flips_same_model`, `history_runs`, `rebuilt_during_run`, `failure_kind`), so a reader can see WHY a lower rule did not get a chance. A row with fewer than 2 prior runs gets `history: insufficient` in its detail; it can still receive any verdict except `KNOWN_FLAKY`.

ja-JP rows: the matcher and token signals are unavailable (no whitespace tokenization). Rules 5 and 6 are skipped for them and the row detail says `static signals skipped: ja-JP`.

## Families

Group red rows by the key `(language prefix of the locale, expected_intent, actual_intent, verdict)`, for example `(es, PlayEpisodeIntent, PlaySongIntent, CONTESTED)`. Sort families by size descending, then by key. A family lists its locales and its utterances.

## CLI

`python3 scripts/nlu_static/cli.py triage [--session ID|latest] [--dir D] [--snapshot f.json] [--history N] [--flaky-min-flips N] [--format md|json] [--out FILE] [--fail-on systematic]`.
- Default session: the latest COMPLETE session; `--session latest` allows an incomplete one and the report header then says so.
- Markdown report layout: a header with session id, git head, row totals and counts per verdict; a section "Look at these first" with the `SYSTEMATIC_CANDIDATE` families; then one section per other verdict in precedence order; each family as a short table (locale, utterance, expected, actual, detail). The report ends with a fixed paragraph stating that the verdicts describe necessary conditions and history, and do not predict Amazon's routing.
- JSON output contains the same data, sorted, for machine use.
- Exit code 0 by default. With `--fail-on systematic` the exit code is 1 when at least one `SYSTEMATIC_CANDIDATE` row exists.
- Output must be byte-identical for the same ledger files, models, baseline and snapshot. Do not print the current time.

- Compute effective models once per locale, not per row.
- Tests in `tests/scripts/test_nlu_static_triage.py`: build synthetic ledger files and tiny models in `tmp_path`. One test per verdict that proves the rule fires, and one PRECEDENCE test per adjacent pair proving the earlier rule wins when both apply (for example a row that is both vocabulary-absent and contested must be `FIXTURE_VOCAB`). One family-grouping test. One determinism test.

Without a snapshot the verdict must be `CONTESTED` or `SYSTEMATIC_CANDIDATE` according to what the matcher finds on the committed model (assert whichever the matcher truly returns, and state it in the test name); with a snapshot whose SeriesName lacks the title the verdict must be `FIXTURE_VOCAB` with detail `absent in live catalog`.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Read the STATE CHANGE note on the parent JF-954 first. Three precisions. (1) Rule 3 (FIXTURE_VOCAB) takes the row's `expected_slots` from the ledger record (JF-954.5 stores them verbatim), builds the fixture-row shape that `check_fixture_rows` expects, and never opens `tests/integration/fixtures/`. (2) JF-954.3 defines an extra status `ABSENT_IN_LIBRARY_SEED_ONLY` (value missing from a name-level snapshot but present in the committed seed, so probably present live because the plugin merges seeds). That status must NOT trigger FIXTURE_VOCAB; it is carried in `vocab_status` so the reader sees it. Only plain `ABSENT` and `FIXTURE_SLOT_UNKNOWN` trigger the verdict. (3) In committed mode (no snapshot) an `ABSENT` on a CATALOG type means only "not in the seed", which is normal for fixtures that use real library items; in that mode rule 3 fires only for STATIC types and for FIXTURE_SLOT_UNKNOWN. Say in the report header which mode was used and recommend re-running with a snapshot when none was given.

The description's realistic scenario test that reads the row from the committed es-ES fixture is SUPERSEDED by the new acceptance criterion: the ledger and its rows are synthetic and inline.
