## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Filed 2026-10-01 same-turn from the JF-686 code-review round (high effort, findings 1 and 2 of 3; finding 1 code-verified by the worker before filing). The JF-686 serve-side fix (the redirect no longer drops ?start=) is correct and pinned, but review traced the mint side and found the fixed serve path is LATENT for one-chapter books: no production launch can deliver a positive ?start= to a single-chapter book today, so the user-visible restart the task title describes persists at the TRACKING layer.

FINDING 1 (verified): a one-chapter book can never hold a tracker position.
- The single-chapter redirect re-mints a CHAPTER-scoped token and the song core builds segment URLs keyed by the CHAPTER id (VideoAudioController.cs hlsBaseUrl = /alexaskill/api/video-audio/{chapterId}/segments/).
- GetSegment's write gate ShouldRecordPositionProgress records ONLY when GetItemById(itemId) is a Folder (JF-499 W1, VideoAudioController.cs ~3540); the chapter is a leaf (AudioBook/Audio), so nothing is recorded under EITHER the chapter key (write-only dead weight by design) or the book key the resume path reads.
- Every resume-URL mint site therefore sees a permanently cold tracker for one-chapter books and refuses to mint ?start=>0: ResumeIntentHandler.TryBuildNativeControlsBookResumeAsync (trackedTicks <= 0 returns null, chapter-relative UserData fallback deliberately cannot slice, JF-567), PlayBookIntentHandler (trackedTicks > 0 gate), LaunchRequestHandler (useResumePlaylist = true only on trackedTicks > 0), YesIntentHandler (the offeredTicks fallback only runs when the offer set UseResumePlaylist, which required tracker > 0 at offer time).
- Net effect: StreamHlsAudiobook's single-chapter branch only ever binds startTicks = null in production; the JF-686 sliced serve runs solely under the unit test's synthetic direct call. Multi-chapter books are unaffected (the concat cache keys segments by the parent Folder, which the gate records).

FIX DIRECTIONS (needs a design decision, NOT a drive-by):
(a) Canonicalize at record time: when GetSegment's itemId resolves to a LEAF whose parent is an audiobook folder, record under the parent book key (ResumeMath.GetAudiobookBookKey equivalent). MUST mind the JF-625 MusicAlbum interplay: album concat serves segments keyed by the ALBUM id (a Folder, already recorded) and album resume sums track offsets via AlbumPlayService rather than reading the tracker, so a leaf-under-album canonicalization must not start feeding album keys into the audiobook tracker.
(b) Re-key the redirect's segment URLs and token to parentId (segments cached under the chapter's dir, so FindSegmentPath + token scoping would all move): bigger blast radius, touches the JF-309 token contract and the JF-685 no-token seam documentation.

FINDING 2 (verified, pre-existing on all three resume routes, JF-686 only extends the exposure to the song serve): a ?start= beyond the playlist's total duration yields a ZERO-SEGMENT playlist. BuildSlicedPlaylist's EXTINF walk returns null for beyond-total (and for missing/unparseable durations), the flat-divisor fallback then computes a startSegment past the last segment, and the emitter keeps nothing: the device receives header + MEDIA-SEQUENCE:N + ENDLIST with no segments and fails playback. The route is [AllowAnonymous] with the token in the URL, so any URL holder can append &start=huge; a stale tracker position over a shortened item reaches the same shape. DESIGN CONSTRAINT the worker hit live: the obvious guard (zero-keep slice serves the base unsliced) CONTRADICTS two existing green pins, BuildResumePlaylist_Sliced_NoExtinf_FallsBackToFlatDivisor and BuildResumePlaylist_Sliced_UnparseableExtinf_FallsBackToFlatDivisor, which pin the flat fallback's zero-keep MEDIA-SEQUENCE rewrites on no-EXTINF / 2-segment playlists. The guard therefore needs to DISTINGUISH beyond-total (metadata proved the position unplayable) from metadata-missing (the fallback exists precisely for that), i.e. a richer TryResolveStartSegmentByExtinf result, not a silent re-pin of the fallback contract.

## Design note (worker, 2026-10-02, before implementation)

THE GATE DECISION (final shape, after the code-review round): candidate (2), record-time canonicalization gated on `AudiobookItems.IsAudioBook(item) && item.ParentId != Guid.Empty` (an AudioBook leaf WITH a parent). `GetSegment`'s tracking block becomes one helper that resolves the READ-ALIGNED key: the Folder arm keeps the JF-499 W1 shape verbatim (record under the item's own id: the multi-chapter audiobook concat AND the JF-625 album concat, whose MusicAlbum parent is a Folder; see the FACT CORRECTION below for why album-key entries are load-bearing, not dead weight); the NEW AudioBook-leaf arm records under `ResumeMath.GetAudiobookBookKey(item)` (the ParentId), the identical expression all four mint sites read (ResumeIntent ~501, PlayBook ~282, LaunchRequest ~294, YesIntent via GetAudiobookStartTicks).

SCOPE OF THE LEAF ARM (code-review finding 1 corrected this): the arm covers exactly the ONE producer, the one-chapter redirect (chapters query is IncludeItemTypes=AudioBook, so chapters[0] IS an AudioBook whose ParentId is the book folder; the single chapter is the whole book, so the leaf's own timeline is the book timeline). The root-level single-file book (EMPTY ParentId, served by the plain song route because BuildVideoAppAudioResponse's isAudioBook branch requires a non-empty ParentId) is deliberately EXCLUDED: recording it would warm a key whose mint builds `audiobook/{ownId}/stream.m3u8`, and the concat endpoint's children query under a LEAF returns zero chapters (404), so the recorded position would arm a dead URL; the key must stay cold for resume to keep the working plain single-item launch. Pinned by GetSegment_RootLevelAudioBookLeaf_EmptyParentId_DoesNotRecord. A multi-chapter book's chapters can never be served leaf-keyed: the builder routes every AudioBook with a non-empty ParentId to the concat URL keyed by the parent Folder.

WHY NOT candidate (1) as stated (widen the gate so the leaf records under its own key): pure dead weight, the exact JF-499 W1 shape the gate exists to prevent; no mint site ever reads a chapter-leaf key, so the tracker would stay cold for one-chapter books anyway. WHY NOT the `IsAudioBookOrChapter` helper as the predicate: its second arm (a plain Audio item under an AudioBook ancestor) would key ordinary song-segment fetches under their ancestor/subfolder ids, which no mint site reads (the mints read chapter.ParentId of the chapters-query result); dead weight again, plus a music-plays-alias-into-book-keys pollution vector.

JF-625 CONSTRAINT ANALYSIS (why the gate is Folder-only today and what the widening must not reopen): the Folder arm serves BOTH concat shapes, the audiobook parent folder and the MusicAlbum (queue-as-concat serves segments keyed by the ALBUM id, a Folder). FACT CORRECTION (verified in code during the /simplify round, against this task's own Description line "(a) ... album resume sums track offsets via AlbumPlayService rather than reading the tracker"): AlbumPlayService DOES read the tracker (AlbumPlayService.cs ~630, JF-625 criterion 3); in seek mode the tracker's album position OVERRIDES server-side UserData as the resume truth, mapped onto the track timeline by the runtime-prefix walk. Album entries are therefore LOAD-BEARING, and the JF-625 hazard of an Audio-leaf-to-parent canonicalization is stronger than dead weight: an ordinary song play (every song's single-item HLS segments) would write a track-local 4s-timeline index under the album key whose reads count the 10s concat timeline, actively poisoning album resume. My diff leaves the Folder arm byte-identical, so album behavior is untouched either way. The AudioBook-type predicate cannot catch an album track (Audio != AudioBook), a podcast episode, or a TV episode. Pinned by the new JF-625 regression pin.

THE TIMELINE TRANSLATION (the arithmetic the task text does not mention but the fix must carry): the redirected core is the SONG core, cutting SongHlsSegmentSeconds=4 segments, while the tracker's GetPositionTicks arithmetic is the 10s concat timeline (AudiobookPositionTracker.SegmentDurationSeconds, the documented LOAD-BEARING COUPLING). A raw 4s index recorded as-is would be read back 2.5x past the actual listening point (segment 150 = 10 minutes listened would read as 24:50). New tracker method `RecordScaledSegment(bookParentId, segmentNumber, segmentSeconds)`: translate index = segmentNumber * segmentSeconds / SegmentDurationSeconds (integer floor, conservative), then the existing RecordSegment path. The 10s const stays single-owner in the tracker; the controller contributes only its own fact (SongHlsSegmentSeconds).

THE OVERRUN DECISION (finding 2): NO bound added, deliberately:
1. The mint-site bound as the task sketches it (trackedTicks vs the item's runtime) is UNSOUND for multi-chapter books: trackedTicks is BOOK-absolute while the mint item is the resume CHAPTER; min() would clamp every deep-book resume to the chapter's own runtime (a legit 5h book position clamped against chapter 3's 30min runtime slices the book at 30min).
2. The shared-chokepoint bound is excluded by the task's own design constraint: a blanket zero-keep guard contradicts the two green flat-divisor pins (BuildResumePlaylist_Sliced_NoExtinf_FallsBackToFlatDivisor, BuildResumePlaylist_Sliced_UnparseableExtinf_FallsBackToFlatDivisor; the second literally pins a zero-keep MEDIA-SEQUENCE rewrite on a 2-segment garbage playlist), and the distinguishing shape (a richer TryResolveStartSegmentByExtinf result: BeyondTotal vs MetadataMissing) is a behavior change to the live-verified shared slicing mechanism shared with the multi-chapter and episode paths, out of this task's mandate.
3. The record shape CANNOT mint an over-total position on stable content: the recorded index derives from segments actually fetched of the current encode, so (translatedHwm - 1) * 10s is structurally below the content total. The over-total reachables are (a) a URL holder appending &start=huge (they hold the item-scoped token already, i.e. can fetch every segment directly, so the zero-segment playlist harms only their own playback); and (b) a stale tracker position over SHRUNKEN content under the same folder GUID, a pre-existing multi-chapter exposure, rare (the folder id survives a content swap), visible (playback fails once), and with a user exit: StartOver clears the tracker (StartOverIntentHandler.ClearRestartedPosition), so the wedge self-heals on the next explicit restart.

PINS (red proofs per shape): (1) RECORD: GetSegment_SingleChapterAudioBookLeaf_RecordsUnderBookKeyOnConcatTimeline, seg_0015 on an AudioBook chapter leaf records 50s under the PARENT book key (15*4/10=6, (6-1)*10s) and nothing under the dead leaf key; red: gate reverted to Folder-only, the book-key assert reads 0. (2) MINT: ServerProgressFallback_OneChapterBook_BookKeyPosition_MintsSlicedResumeUrl (ResumeIntentHandlerServerProgressTests), a one-chapter arrange whose tracker holds the translated shape the record pin proves GetSegment writes, the VideoApp source carries audiobook/{parent}/stream.m3u8?start=50s&token=; red: the same position seeded under the LEAF key (candidate 1's literal shape) leaves the mint cold, the fresh no-start launch answers and the ?start= assert flips. (3) JF-625 REGRESSION: GetSegment_AlbumTrackLeaf_DoesNotRecordUnderAnyKey, a plain Audio track under a MusicAlbum records nothing under the track id NOR the album id; red: the gate widened to any Audio leaf canonicalizing to ParentId flips the album-key assert. (4) ROOT-LEVEL EXCLUSION (code-review finding 1): GetSegment_RootLevelAudioBookLeaf_EmptyParentId_DoesNotRecord, an AudioBook leaf with an empty ParentId records nothing; red: the arm's ParentId condition dropped flips the assert positive (and would arm the dead audiobook/{ownId} resume URL).
