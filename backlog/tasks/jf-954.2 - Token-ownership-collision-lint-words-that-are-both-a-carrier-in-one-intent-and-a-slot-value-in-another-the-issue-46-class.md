## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
## Why

Issue #46 (de-DE): "spiele das Lied die streithörnchen" was routed to MediaInfoIntent instead of PlaySongIntent. Root cause found only after days of live probing: the word "Lied" was a synonym inside the custom slot type MediaInfoType (used by MediaInfoIntent for "what song is this" questions) and at the same time a literal carrier word in PlaySongIntent samples ("Spiele das Lied {song}"). For titles Amazon does not know, the trainer preferred the intent whose slot type owned the word. This collision is visible in the model files with no Amazon call. This task makes it a build-time warning. Read parent JF-954 first; its "Rules that apply to EVERY subtask" section is binding. Depends on JF-954.1, which provides `tokenize`, `normalize_text`, `is_whitespace_tokenized`, `build_effective_model`, `load_snapshot` and the CLI skeleton in `scripts/nlu_static/`.

## Definitions (implement exactly these)

For one locale's effective model:
- CARRIER of a sample: the token list of the sample after removing every `{slot}` placeholder.
- ENTRY of a slot type: each value and each synonym, as a token list.
- A slot type T is USED BY intent J when J declares a slot of type T.

Finding kinds:
- `CARRIER_VS_VALUE`: an entry of custom type T appears as a contiguous token sequence inside the carrier of at least one sample of intent I, where I does NOT use T and at least one other intent J uses T. One finding per (locale, T, entry, I). The finding records the intents J, the number of samples of I containing the entry, and the alphabetically first such sample as the example. This is the issue #46 shape (T = MediaInfoType, entry = "lied", I = PlaySongIntent, J = MediaInfoIntent).
- `VALUE_IN_TWO_TYPES`: the same normalized entry text exists in two different custom types of the same locale. One finding per (locale, entry, sorted pair of type names).
- `CATALOG_VS_MODEL` (only when a catalog snapshot is supplied, CLI only, never in the validator and never baselined): a snapshot entry of a catalog type whose full normalized text equals (a) a complete slot-free sample of any intent, or (b) an entry of a STATIC custom type. Example: a library song titled "Stop" or "Jazz". Output per locale: the count per sub-kind and the first 50 findings in sorted order.

Finding identity (used for sorting and for the baseline) is the string `locale|kind|type-or-types|entry|intent-or-empty`.

## Baseline

Many `CARRIER_VS_VALUE` findings are legitimate design (a MediaType value "album" also appears in "play the album {album}"). The lint therefore warns only on findings that are NOT in a committed baseline file `scripts/nlu_static/token_collision_baseline.json` (a sorted JSON list of identity strings). Model on the existing baseline-aware pattern in `scripts/validate_locales.py` with `scripts/locale_baseline.json`.
- CLI: `python3 scripts/nlu_static/cli.py tokens [--locale X] [--snapshot f.json] [--all] [--update-baseline]`. Default prints only non-baselined findings; `--all` prints everything with a `baselined: true/false` field; `--update-baseline` rewrites the baseline from the current committed models and prints how many identities were added and removed. The CLI also lists STALE baseline identities (in the baseline, no longer produced).
- Validator: add a warning phase to `scripts/validate_interaction_models.py` titled "Phase 11: token-ownership collisions (JF-954 warning check)" using `run_warning_phase`. It reports non-baselined `CARRIER_VS_VALUE` and `VALUE_IN_TWO_TYPES` findings in committed mode. ja-JP prints the SKIP line.
- Generate and commit the initial baseline from the committed models as part of this task. Before committing it, check whether the de-DE findings include MediaInfoType entries "lied", "song" or "titel" against PlaySongIntent, and write what you found in the task notes (JF-933 tracks that defect and may or may not have landed; do NOT edit the de-DE template to fix it, only report).

## Guidance

- Build one inverted index per locale: token to list of (intent, sample index, position). Match multi-token entries by looking up the first token and verifying the following positions. Do not loop over all samples for every entry.
- Skip entries that are empty after tokenization.
- Tests in `tests/scripts/test_nlu_static_tokens.py` using synthetic models built as dicts. Required regression test: a mini de-DE model with MediaInfoIntent using MediaInfoType (value "info", synonyms "Lied", "Song") and PlaySongIntent with samples "Spiele das Lied {song}" and "Spiele {song}" must yield exactly one `CARRIER_VS_VALUE` finding for entry "lied" against PlaySongIntent, and none for "song" (it is only a slot name there, not a carrier token: placeholders are removed before tokenizing).
- Negative test: an entry that appears only in carriers of an intent that itself uses the type yields no finding.
- Extend `docs/nlu-static-analysis.md` with a section: what the lint finds, how to read a finding, when to baseline it and when to fix the model, with the issue #46 story as the worked example.

## Out of scope

Fixing any finding in templates or models. Any SMAPI call. The subsumption analysis (separate subtask).
