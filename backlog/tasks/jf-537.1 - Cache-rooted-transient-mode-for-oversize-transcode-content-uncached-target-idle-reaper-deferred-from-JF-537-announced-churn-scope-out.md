## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
JF-537 shipped the ANNOUNCED-CHURN resting point: a transcode-tier estimate above the cache cap logs a Warning at encode entry (VideoAudioController.TranscodeEstimateExceedsCacheCap) and the encode still runs inside the cache, so oversize content keeps re-encoding on every replay. The rejected alternative, encoding oversize content to an UNCACHED target so the bytes never count against the cap and never get swept, was scoped out with a 5-point evidence case documented on TranscodeEstimateExceedsCacheCap's doc comment (VideoAudioController.cs, JF-537 delta): (1) segment resolution keys on the cache root (VideoAudioCache.FindSegmentPath -> in-memory RegisterHlsDirectory lookup + FindHlsDirectoryByScan bounded to the cache dir), (2) the concurrent-encode dedup detects in-flight work via GetCachedHlsPlaylist on the cache path, (3) the JF-531 pre-written playlist is served from the same dir, (4) encoding outside the cache bypasses the JF-428 reserve/pin budget machinery, and (5) an uncached dir needs playback-stop detection to be deletable and VideoApp emits no playback events, so an idle-reaper subsystem (segment-fetch recency as the only liveness signal) would have to be built. That refactor is this task: give oversize transcode content a cache-exempt target dir with its own registration/scan/dedup plumbing and recency-based reaping, so oversize replays stop paying the full re-encode AND stop churning the capped cache. Decide first whether the churn actually hurts: the Warning landing in JF-537 may show the affected content is rare enough that the refactor never pays for itself; close as won't-do with log evidence if so.

## Notes

<!-- SECTION:NOTES:BEGIN -->
DESIGN (design-first, 2026-10-05, pre-implementation; the orchestrator dispatch
directed implementation over the won't-do branch, and the churn-hurts question
is answered by the JF-534/JF-500 live evidence rather than a Warning-count log
audit: the 51-min HEVC episode measurement proves real library content rides
the transcode tier, and the round-UP estimator makes every 61..120min transcode
oversize against the 4096 default, i.e. the canonical 1080p movie shape pays
the full ~27min-of-CPU re-encode on EVERY replay today):

1. WHICH CONTENT QUALIFIES. Exactly the JF-537 predicate, unchanged: the EPISODE
   TRANSCODE tier only, when TranscodeEstimateExceedsCacheCap(
   EstimateEpisodeTranscodeEncodeBytes(runtime), _cache.EffectiveCacheCapMB).
   The remux tier, song, audiobook, and the two audio variants stay
   cache-rooted (JF-537's scope pin is inherited: remux copies at the source's
   own bitrate and replays at ~20x realtime; the audio tiers reserve ~96MB/h).
   THRESHOLD SOURCE: EffectiveCacheCapMB, the same number the sweep enforces,
   so the transient decision can never disagree with the cap. A cap change
   between plays is safe: the SERVE paths resolve BOTH roots (cache first), so
   a transient entry minted before a cap raise keeps serving, and the next cold
   encode picks its root by TODAY's estimate.

2. THE TRANSIENT ROOT. {CachePath}/alexaskill-video-audio/transient/
   {itemId}_{artModifiedTicks}/: cache-ROOTED (same filesystem, subtree of the
   cache root), invisible to the cap sweep BY CONSTRUCTION.
   EvictIfNeededCore enumerates GetFiles("*.mp4") and GetDirectories("*_*")
   both TopDirectoryOnly; "transient" carries no underscore and holds no
   top-level stream.m3u8, so its bytes never count toward the cap and the cap
   sweep never deletes them. Segment URLs are unchanged; segment RESOLUTION
   becomes root-agnostic. The JF-731 test backstop needs no change: its
   pid-file half enumerates CacheDir recursively and its /proc half matches the
   temp dir in argv, and both cover transient subtrees.

3. ENCODE PATH (StreamHlsEpisodeCore). hlsDir := the transient path iff
   oversize, else the cache path (today's line). The JF-537 churn Warning is
   REPLACED by an Information "transient mode" line naming item/estimate/cap
   (the churn it announced no longer exists: the entry is retained until idle).
   StartFfmpegProcessGatedAsync keeps the gate and the episode transcode slot
   (the DoS/CPU bounds are orthogonal to where bytes land) and keeps pinPath =
   hlsDir (the pin is path-keyed; the reaper honors it), but passes
   estimatedEncodeBytes 0 on the transient leg: the JF-428 pre-encode headroom
   exists to make room IN THE CACHE for the incoming encode, and a transient
   encode writes nothing there. Reserving 6GB of headroom against a capped
   cache the encode will never enter is precisely the real-cache eviction this
   task removes. Headroom 0 is the sweep's post-encode shape (full-cap
   target), so the cap is still enforced. CleanupHlsStub and
   DeleteHlsEncodeDebris clean BOTH roots' (key, ticks) dirs (called under the
   per-item lock; the lock key is the mp4 path, shared by both roots, so
   same-key encodes stay serialized). RegisterHlsDirectory registers the
   RESOLVED dir path (new path-taking overload; the (itemId, ticks) form stays
   for the cache-rooted paths).

4. SERVE PATHS (root-agnostic resolution, cache root preferred).
   GetCachedHlsPlaylist checks the cache playlist, then the transient playlist
   (RecordAccess on whichever dir hits). That one change covers the episode
   fast path, the in-lock double-check, and the concurrent-encode dedup, and is
   a guaranteed miss for keys that never go transient (variants, audiobook,
   album: their dirs cannot exist there). TryServePrewrittenEpisodePlaylist
   checks the cache prewrite, then the transient prewrite.
   FindHlsDirectoryByScan scans the cache root, then the transient root (the
   restart fallback for segment serving and the JF-503 hold path).
   ValidateHlsCacheAsync's debris cleanup deletes the generation dir the
   verdict was SERVED FROM (Path.GetDirectoryName(cached.FullName)) instead of
   re-deriving the cache path: a key holding both a transient-debris dir and a
   live cache dir must lose only the transient one (CleanupHlsGenerationAt
   core; the (itemId, ticks) wrapper stays for the other callers).

5. THE IDLE REAPER. Owner: VideoAudioCache. A transient dir is reaped when its
   last liveness signal (the recorded serve in _lastAccessUtc, refreshed by
   every playlist and segment fetch via RecordAccess, else the directory's own
   write time: every ffmpeg write here is a new directory entry) is older than
   TransientIdleReapTtl (default 30 minutes, internal test seam like
   PlaybackEvictionExemptionTtl), and it holds no pin (an in-flight encode is
   never reaped; a fresh encode dir is double-protected by its pin and its
   fresh mtime). 30min = 3x the 10-minute playback-pin window: far above any
   live fetch cadence, sized to survive a long pause, while bounding disk
   hold. TRIGGER: the POST-ENCODE eviction sweep (the public EvictIfNeeded the
   monitors run via Task.Run after an encode completes), NOT the pre-encode
   budget sweep (code-review round: reaping inline before every gated encode
   would put recursive multi-GB deletes on the Alexa play path for no budget
   reason; a transient encode reserves nothing in the capped cache), and NO
   background timer (a timer-owned reaper would leak per test-constructed
   cache instance and need host-lifetime disposal the cache singleton does
   not have). Honest bounds: (a) between skill uses an idle entry lingers
   until the next encode completes anywhere; (b) the transient root has NO
   byte cap. A byte budget below the entry size is structural here
   (qualification means estimate > cache cap, so any cap-derived budget reaps
   idle entries immediately, collapsing the TTL to zero and the replay
   benefit with it); the hold is bounded by the watched entry plus entries
   idle within the TTL (~2 oversize entries worst case). Transient DEBRIS
   (killed encode, no ENDLIST, not live) is verdict-cleaned on the next
   request for its key (the no-ENDLIST row) exactly like cache debris; the
   TTL reaper is the backstop for debris never requested again. The reaper's
   scan carries its own JF-431-class cost tripwire (the root is unbounded by
   design, so its growth must stay visible), and the cap sweep's directory
   enumeration excludes the transient subtree by an explicit name check, not
   only by glob shape (code-review round).

6. CONFIG SURFACE: none (out of the declared task surface); the threshold
   reuses EffectiveCacheCapMB, the TTL is an internal seam.

7. TESTS (JF-765-era hermeticity kept: no ambient ffmpeg; the recording fake
   derives its output dir from the playlist argv, so it writes into the
   transient dir unchanged). RED PROOF (both TFMs, run on the unmodified base
   first): a seeded REAL cache (files totaling more than half a small cap but
   under the cap) plus a 2h HEVC episode (estimate 6144MB vs a 2MB cap)
   encoding through the controller asserts (a) the serve still works, (b) the
   encode landed under the TRANSIENT root with nothing at the cache-root dir,
   (c) EVERY seeded cache file survived: the pre-encode sweep must not wipe the
   real cache. On the base: headroom 6144MB floors the target at half the cap
   and evicts the seeds, and the encode lands in the cache root, so both (b)
   and (c) go red. Supporting pins: under-cap transcode stays cache-rooted;
   replay serves from the transient root without re-encoding (ENDLIST-carrying
   fake); segment resolution from the transient root (registered) and after a
   simulated restart (scan fallback); the reaper (old-mtime dir reaped,
   recently-served and pinned dirs survive, cache-root entries untouched by
   the reap); the sweep never counts transient bytes; the verdict cleans the
   served-from dir only. Of the three JF-537 tests: the over-cap warning test
   is REWRITTEN to the transient-mode expectation (the churn it pinned is gone
   by design); the under-cap and remux-scope tests stand unchanged.
