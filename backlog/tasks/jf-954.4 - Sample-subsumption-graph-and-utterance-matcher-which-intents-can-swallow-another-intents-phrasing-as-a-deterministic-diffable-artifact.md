## Why

Most NLU regressions in this project are intent competition: a short carrier with a free-text slot in one intent can also parse a phrase that belongs to a more specific intent, and Amazon's trainer then decides by weights we cannot see. Verified example in the committed es-ES model: PlaySongIntent has the sample `Pon {song}` (slot type AMAZON.MusicRecording, free text) and PlayEpisodeIntent has `pon {series_name} temporada {season_number} episodio {episode_number}`. Everything the second sample can produce is also a valid reading of the first. Rows on such ground are marginal by construction: after any rebuild they may flip. Rows with no rival reading are not marginal, and a red there deserves attention.

We cannot predict the winner. We CAN compute, deterministically, which rival readings exist. That gives three things: a review artifact (the diff of the graph between two commits shows new competition introduced by a template change), a triage signal (contested versus uncontested fixture rows), and a neighbour relation for test selection. Read parent JF-954 first; its "Rules that apply to EVERY subtask" section is binding. Depends on JF-954.1 (`build_effective_model`, `classify_slot_type`, `tokenize`, `is_whitespace_tokenized`, CLI skeleton in `scripts/nlu_static/`).

## Part A: pattern model (implement exactly this)

A PATTERN is one sample turned into a sequence of items: literal tokens (via the shared `tokenize` on the text between placeholders) and slot items. Each slot item has a class from `classify_slot_type`: FREE, NUMERIC, STRUCTURED, CLOSED (with its type name). UNKNOWN_BUILTIN is treated as FREE and the type name is collected into an `unclassified_types` list in the output.

A WITNESS is the abstract utterance a sample generates: the same sequence where each slot becomes one class token: `<FREE>`, `<NUM>`, `<STRUCT:AMAZON.DURATION>` (type name included), `<CLOSED:TypeName>`.

Pattern P MATCHES witness W when the whole of W can be consumed left to right:
- a literal token matches the identical literal token;
- a FREE slot matches one or more consecutive items of ANY kind (literals or class tokens);
- a NUMERIC slot matches `<NUM>` only;
- a STRUCTURED slot matches the class token of the same type only;
- a CLOSED slot of type T matches (a) `<CLOSED:T>`, (b) `<CLOSED:T2>` when the normalized entry sets of T and T2 intersect, (c) a run of literal tokens equal to the token list of some entry of T.
Implement with memoized recursion or dynamic programming over (pattern index, witness index). Do not translate to `re` patterns (vocabulary alternations blow up).

## Part B: the graph

Nodes are intents of one locale. For every ordered pair of different intents (A, B), for every sample b of B and sample a of A: if the skeletons are equal item by item (slots compared by class and, for CLOSED, by type) the pair is IDENTICAL; otherwise if pattern(a) matches witness(b) it is a SWALLOW. An edge A to B exists when at least one pair qualifies. The edge records: `kind` (IDENTICAL if any identical pair, else SWALLOW), `swallowed` (number of distinct B samples matched by at least one A sample), `total` (number of B samples), and up to 3 `examples` as `[a_sample, b_sample]`, chosen as the first three in sorted order. The output also lists `universal` intents: those that swallow at least one sample of more than half of the other intents (typical for a bare `{query}` carrier).

Output file format (JSON, sorted keys, edges sorted by from, to):
```json
{"schema": 1, "locale": "es-ES", "mode": "committed", "unclassified_types": [], "universal": [], "edges": [{"from": "PlaySongIntent", "to": "PlayEpisodeIntent", "kind": "SWALLOW", "swallowed": 2, "total": 14, "examples": [["Pon {song}", "pon {series_name} temporada {season_number} episodio {episode_number}"]]}]}
```
Performance: the largest locale has 1860 samples and all 17 total 9646. A naive all-pairs pass is acceptable only if the full 16-locale build stays under 120 seconds on the workstation. Cheap accelerations, in this order: de-duplicate identical skeletons within an intent before matching; skip a pair early when pattern a starts with a literal that differs from the first item of witness b, or ends with a literal that differs from the last item. Record the measured time.

## Part C: utterance matcher and fixture classification

`match_intents(utterance, effective_model) -> list` matches a REAL utterance (plain tokens) against every sample pattern, full match, with these rules: literal equals token; FREE matches one or more tokens; CLOSED matches a token run equal to an entry of the effective type; NUMERIC matches exactly one token of any kind; STRUCTURED matches one to four tokens of any kind. The NUMERIC and STRUCTURED rules are deliberate over-approximations ("uno", "30 segundos"); the output means "a reading exists", not "Amazon will choose it". Each hit has `intent`, `sample`, `specificity` (number of literal tokens in the sample). Return, per intent, its hit with the highest specificity, sorted by specificity descending then intent name.

`classify_fixture_row(row, effective_model)` returns one of:
- `UNCONTESTED`: only intents listed in `expected_intent` match;
- `CONTESTED`: an expected intent matches and at least one other intent matches too; include `rivals` (list of intent, sample, specificity) and the boolean `rival_at_least_as_specific`;
- `NO_SAMPLE_MATCH`: no expected intent has a matching sample (the row relies on trainer generalization, or on vocabulary absent from the effective model); include `rivals`.

## CLI (added to `scripts/nlu_static/cli.py`)

- `graph build --locale X|--all [--snapshot f.json] --out DIR` writes `graph_<locale>.json`.
- `graph diff OLD.json NEW.json` prints added edges, removed edges and edges whose `kind` or `swallowed` changed, sorted. Exit code 0 always; `--fail-on-new` exits 1 when an edge was added.
- `graph diff-git --base <git-ref> [--locale X|--all]` builds the old graph from `git show <ref>:<model path>` and the new one from the working tree, then prints the same diff. This is the reviewer command for a template change.
- `match --locale X "utterance" [--snapshot f.json]` prints the hits.
- `classify-fixtures --locale X|--all [--snapshot f.json]` prints sorted JSON rows with `locale`, `utterance`, `expected_intent`, `classification`, `rivals`, `rival_at_least_as_specific`. The triage subtask consumes this JSON; keep these field names.

ja-JP prints `SKIP ja-JP: no whitespace tokenization` in every command.

## Guidance

- Keep pattern compilation, matching, graph building and classification as pure functions in separate small modules (`patterns.py`, `graph.py`, `matcher.py`); the CLI only wires them.
- Tests in `tests/scripts/test_nlu_static_graph.py`. Unit-test the matcher rule by rule with tiny hand-written patterns before testing the graph. Required real-data tests on the committed es-ES model: (1) the graph contains an edge PlaySongIntent to PlayEpisodeIntent whose examples include the pair `Pon {song}` and `pon {series_name} temporada {season_number} episodio {episode_number}`; (2) `classify_fixture_row` for the utterance "pon breaking bad temporada uno episodio tres" with expected PlayEpisodeIntent is `CONTESTED` with PlaySongIntent among the rivals; (3) the same row under a snapshot whose SeriesName is `["Adolescencia"]` is `NO_SAMPLE_MATCH`.
- This task adds NO validator phase: the graph is noisy by nature and belongs in review and triage, not in the blocking CI output.
- Extend `docs/nlu-static-analysis.md`: the pattern rules in plain words, how to read an edge, how to use `graph diff-git` when reviewing a template change, and an explicit paragraph on limits. Include this known counter-example so nobody over-trusts the tool: in an es-US lab ablation on 2026-11-23, removing five bare PlaySong carriers moved song requests that used untouched carriers ("escucha", "quiero escuchar") to PlayArtistSongsIntent. The graph shows PlayArtistSongsIntent as a neighbour, it does not predict that the trainer would move them.
